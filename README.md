# Campus Sharing Hub — MVP with Supabase

เว็บเช่าของใช้ระยะสั้นสำหรับนักศึกษา พัฒนาต่อจากหน้าเดิมด้วย Vite + JavaScript + Supabase

## ฟีเจอร์ในเวอร์ชันนี้

1. สมัครสมาชิก / เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
2. ลงประกาศสินค้าจริง เก็บลง PostgreSQL และแสดงให้ผู้ใช้คนอื่นค้นหาได้
3. ค้นหาด้วยคำ หมวดหมู่ งบประมาณ และเรียงราคา
4. ส่งคำขอจองพร้อมวันรับ–คืน จุดนัดรับ และหมายเหตุ
5. เจ้าของประกาศอนุมัติหรือปฏิเสธคำขอจองได้ และมีการป้องกันวันจองที่ทับซ้อนกันเมื่ออนุมัติ
6. หน้าบัญชีของฉัน แสดงประกาศของฉัน รายการที่ฉันจอง และคำขอที่ได้รับ พร้อมซ่อน/เปิดประกาศและยกเลิกคำขอที่ยังรออนุมัติ
7. อัปโหลดรูปสินค้าไปยัง Supabase Storage (JPG/PNG/WebP/GIF ไม่เกิน 5 MB) แทนการวาง URL รูปภาพ
8. แผงควบคุมแอดมินสำหรับดูสถิติ ประกาศทั้งหมด คำขอจองทั้งหมด และรายชื่อสมาชิก พร้อมซ่อนประกาศ/อนุมัติหรือปฏิเสธคำขอ
9. แชตส่วนตัวระหว่างผู้เช่ากับเจ้าของประกาศ พร้อมกล่องข้อความและจำนวนข้อความที่ยังไม่อ่าน
10. ศูนย์แจ้งเตือนในฐานข้อมูลสำหรับคำขอจอง การตอบรับ/ปฏิเสธ การยกเลิก ข้อความ และข้อเสนอ
11. ประกาศสิ่งที่ต้องการแบบแชร์ข้ามผู้ใช้ ส่งข้อเสนอพร้อมประกาศสินค้า และตอบรับ/ปฏิเสธจากบัญชี
12. สลับรายการ/แผนที่ Leaflet พร้อมหมุดจากพิกัดที่เจ้าของประกาศระบุเอง และเลือกหรือเลื่อนหมุดจุดรับโดยประมาณได้

ฟีเจอร์ยังไม่รวมการชำระเงินจริง/มัดจำออนไลน์ การยืนยันนักศึกษาแบบอัตโนมัติ หรือกระบวนการจัดการข้อพิพาท

## ความต้องการก่อนเริ่ม

- Node.js รุ่น LTS (มาพร้อม npm)
- บัญชี Supabase และโปรเจกต์หนึ่งรายการ
- อินเทอร์เน็ตเพื่อดาวน์โหลด dependencies

## A. สร้างฐานข้อมูล Supabase

1. เปิด https://supabase.com/ แล้วสร้างโปรเจกต์ใหม่
2. ใน Dashboard เข้า **SQL Editor → New query**
3. เปิดไฟล์ `supabase/schema.sql` จากโฟลเดอร์นี้ คัดลอกเนื้อหาทั้งหมดไปวางใน SQL Editor แล้วกด **Run**
4. ตรวจว่าไม่มี error และมีตาราง `profiles`, `listings`, `bookings` ใน Table Editor

ถ้าโปรเจกต์นี้เคยรัน `schema.sql` เวอร์ชันเก่าแล้ว ไม่จำเป็นต้องลบตารางหรือข้อมูลเดิม ให้เปิด SQL Editor และรัน `supabase/admin_upload_migration.sql` เพื่อเพิ่มระบบรูปภาพ/สิทธิ์แอดมิน จากนั้นรัน migration สำหรับฟีเจอร์ใหม่ด้านล่าง

สำหรับฐานข้อมูลเดิมที่มีตาราง `profiles`, `listings`, `bookings` และ migration แอดมิน/Storage แล้ว ให้เปิด SQL Editor → **New query** แล้วคัดลอกเนื้อหาทั้งหมดจาก `supabase/marketplace_features_migration.sql` ไปกด **Run** หนึ่งครั้ง ไฟล์นี้เป็น migration เพิ่มเติมที่มีอยู่แล้วใน repository; ไม่ต้องสร้าง migration ซ้ำหรือรัน `schema.sql` ทับข้อมูล production โดยไฟล์เพิ่มตาราง `conversations`, `messages`, `notifications`, `wanted_requests` และ `wanted_offers` (ชื่อจริงที่หน้าเว็บเรียกคือ `wanted_offers` ไม่ใช่ `offers`) พร้อม RLS, foreign keys, indexes, triggers, RPC สำหรับแชต/ข้อเสนอ, Realtime และคอลัมน์พิกัดแบบ nullable โดยไม่เติมพิกัดให้ประกาศเดิม

หลัง Run สำเร็จ ตรวจใน Table Editor ว่ามี `conversations`, `messages`, `notifications` และ `wanted_offers` ใน schema `public` (รวมถึง `wanted_requests`) จากนั้นรัน `NOTIFY pgrst, 'reload schema';` ใน SQL Editor เพื่อโหลด schema cache ใหม่ หากมี SQL error ให้หยุดและตรวจ error ก่อนใช้งาน ห้ามลบตารางหรือปิด RLS เพื่อข้าม error

หากเป็นโปรเจกต์ใหม่ ให้รัน `schema.sql`, `admin_upload_migration.sql` และ `marketplace_features_migration.sql` ตามลำดับ ตรวจสอบผล SQL แต่ละไฟล์ก่อนใช้งานจริง ห้ามลบหรือรีเซ็ตตารางเดิมเพื่อใช้ migration นี้

SQL สร้าง Row Level Security (RLS), สร้าง profile หลังสมัครสมาชิก, คำนวณค่าเช่าที่ฝั่งฐานข้อมูล และจำกัดสิทธิ์การดู/แก้ไขข้อมูลด้วยนโยบายฐานข้อมูล

### ระบบหลักฐานชำระเงินและเงินมัดจำ

ก่อนใช้ระบบนี้ ให้ตรวจประวัติ migration ใน Supabase และตรวจว่าติดตั้ง `booking_lifecycle_migration.sql` กับ `rental_handover_reviews_reports_migration.sql` แล้ว จากนั้นเปิดไฟล์ `supabase/payment_deposit_migration.sql` ตรวจสอบ SQL และรันทั้งไฟล์หนึ่งครั้งใน **SQL Editor** โดยไม่รัน `schema.sql` ซ้ำหรือรีเซ็ตข้อมูลเดิม ไฟล์นี้สร้างตาราง/นโยบาย RLS เพิ่มเติมและ private Storage bucket `payment-proofs`; ไม่ได้เชื่อม Payment Gateway หรือโอนเงิน

หลัง migration ผู้ดูแลตั้งคำแนะนำช่องทางชำระเงินที่ตรวจสอบแล้วได้จาก **แผงควบคุมแอดมิน → การชำระเงิน** ผู้เช่าจึงแนบหลักฐานค่าเช่าหรือเงินมัดจำของรายการที่อนุมัติแล้วได้จาก **บัญชีของฉัน → การชำระเงิน** สถานะจะเป็น “รอตรวจสอบ” จนแอดมินตรวจหลักฐาน ไม่ถือเป็นการยืนยันจากธนาคาร ส่วนสถานะคืนเงินจะบันทึกได้หลังดำเนินการโอนเงินจริงนอกระบบและแอดมินยืนยันในหน้าเดียวกัน

### ค่าบริการแพลตฟอร์ม, QR PromptPay และการโอนให้เจ้าของ

ติดตั้งหลัง `payment_deposit_migration.sql` โดยเปิดไฟล์ `supabase/service_fee_promptpay_payout_migration.sql` ตรวจสอบ แล้วรันทั้งไฟล์หนึ่งครั้งใน **SQL Editor** ไฟล์นี้เพิ่มเท่านั้น ไม่ลบตารางหรือข้อมูลเดิม และรันซ้ำได้

- **ค่าบริการ (Service Fee):** ตาราง `platform_fee_settings` (เริ่มต้น 10% ของค่าเช่า ขั้นต่ำ ฿15) และคอลัมน์ `bookings.service_fee` ที่ฐานข้อมูลคำนวณให้ตอนสร้างคำขอจองใหม่ แก้ไขภายหลังไม่ได้ รายการจองเดิมมีค่าเป็น `NULL` (ไม่มีค่าบริการ)
- **ยอดค่าเช่าที่ต้องโอน** = ค่าเช่า + ค่าบริการ (`submit_booking_payment` ถูกแทนที่ให้คิดยอดนี้) ส่วนเงินมัดจำยังแยกเป็นอีกรายการเหมือนเดิม
- **QR PromptPay:** แอดมินตั้งเบอร์/เลข PromptPay และชื่อบัญชีได้ที่ **แผงควบคุมแอดมิน → การชำระเงิน** ผู้เช่าจะเห็น QR พร้อมยอดที่ต้องจ่ายตอนแนบสลิป (QR สร้างในเบราว์เซอร์ด้วย `qrcode` และ `src/payment-helpers.js`)
- **การโอนให้เจ้าของ:** ตาราง `owner_payouts` สร้างรายการอัตโนมัติเมื่อแอดมินยืนยันสลิปค่าเช่าและการเช่าเสร็จสิ้น เจ้าของเห็นในหน้า **การชำระเงิน** แอดมินโอนเงินนอกระบบแล้วกด “บันทึกว่าโอนให้เจ้าของแล้ว”
- **สรุปการเงิน:** แอดมินเห็นค่าบริการที่เก็บแล้ว ยอดค้างโอน และเงินมัดจำที่ถืออยู่ (`admin_platform_finance_summary`)

ระบบนี้ยังไม่เชื่อม Payment Gateway และไม่ได้ตรวจสลิปกับธนาคารอัตโนมัติ ตัวเลขทั้งหมดมาจากสถานะที่แอดมินบันทึก

### ที่อยู่ในประกาศ และธีม Study UI

- ฟอร์มลงประกาศเปลี่ยนจากช่องละติจูด/ลองจิจูดเป็นช่องที่อยู่ช่องเดียว (เช่น `99/1 หมู่ 4 ต.คลองหนึ่ง อ.คลองหลวง จ.ปทุมธานี`) พอกรอกเสร็จระบบจะแยกตำบล/อำเภอ/จังหวัดให้อัตโนมัติ ค้นหาตำแหน่งด้วย OpenStreetMap Nominatim แล้วปักหมุดบนแผนที่ (`src/address-geocode.js`) ปรับหมุดเองได้โดยแตะหรือลากบนแผนที่
- รัน `supabase/listing_address_migration.sql` เพื่อเพิ่มคอลัมน์ที่อยู่ในตาราง `listings` (ประกาศเป็นข้อมูลสาธารณะ ที่อยู่จึงแสดงให้ทุกคนเห็น) ถ้ายังไม่ได้รัน ระบบจะบันทึกประกาศโดยไม่มีที่อยู่และแจ้งเตือน
- ธีมหน้าตาใหม่อยู่ใน `src/theme-study.css` (โทนสีคราม ปุ่มทรงแคปซูลแบบกดยุบ ฟอนต์ Noto Sans Thai + Archivo) โหลดต่อจาก `styles.css`
- ธีมที่ใช้อยู่ตอนนี้คือ `src/theme-borrow.css` (ตามดีไซน์ Borrow App: พื้นครีม ปุ่มหลักสีเขียวมิ้นต์ ไฮไลต์เหลือง การ์ดสีพาสเทลตามหมวด) `index.html` ลิงก์ไฟล์นี้แทน `theme-study.css` ซึ่งยังเก็บไว้ในโปรเจกต์ สลับกลับได้โดยแก้ลิงก์บรรทัดเดียว
- แอนิเมชันทั้งหมดอยู่ใน `src/animations.css` + `src/animations.js` (ลิงก์ต่อจาก theme-borrow.css และ import ใน main.js): hero ค่อย ๆ ขึ้น, การ์ดเด้งเข้าทีละใบเมื่อเลื่อนถึง, ริบบิ้นหมวดหมู่วิ่ง, รูปทรงลอย, ปุ่มเด้ง/ประกาย, กระดิ่งสั่นเมื่อมีแจ้งเตือนใหม่, โมดัล/ทอสต์เด้ง, คอนเฟตตีเมื่อทำรายการสำเร็จ, หมุดจุดนัดตกลงบนแผนที่ ทั้งหมดปิดอัตโนมัติถ้าผู้ใช้ตั้งค่า reduced motion ถ้าไม่ต้องการก็ลบลิงก์ CSS กับบรรทัด import ออกได้โดยไม่กระทบฟีเจอร์อื่น

### ปักหมุดจุดนัดรับ/คืนของ และนำทาง

รัน `supabase/meeting_points_route_migration.sql` หลังไฟล์ค่าบริการ ไฟล์นี้เพิ่มคอลัมน์พิกัด `pickup_point_*` / `return_point_*` ในตาราง `bookings` และฟังก์ชัน `set_booking_meeting_points` (ไม่ลบข้อมูลเดิม รันซ้ำได้)

- ผู้เช่าปักหมุดจุดรับและจุดคืนได้ตั้งแต่ตอนส่งคำขอจอง (ไม่บังคับ) ทั้งผู้เช่าและเจ้าของแก้ไขหมุดได้ในหน้า **รายการที่ฉันจอง / คำขอที่ได้รับ** ระหว่างรออนุมัติหรือกำลังเช่า และอีกฝ่ายจะได้รับแจ้งเตือน
- พิกัดจริงเก็บในรายการจอง จึงเห็นเฉพาะคู่สัญญาและแอดมินตาม RLS เดิม ไม่แสดงในประกาศสาธารณะ
- ปุ่ม **นำทางไปจุดรับ / จุดคืน** ใช้ตำแหน่งปัจจุบันจากเบราว์เซอร์ (ต้องเปิดผ่าน HTTPS และอนุญาตตำแหน่ง) แล้ววาดเส้นทางเดินหรือขับรถด้วย OSRM ของ FOSSGIS (`routing.openstreetmap.de`) ถ้าคำนวณไม่ได้จะแสดงระยะเส้นตรง และมีปุ่มเปิดเส้นทางเดียวกันใน Google Maps
- โค้ดอยู่ใน `src/meeting-map.js`

### โปรไฟล์ส่วนตัวและหลักฐานการรับ–คืน

หลังจากตรวจ dependencies และรัน migration ก่อนหน้าที่ยังขาดแล้ว ให้ตรวจสอบไฟล์ `supabase/profile_contact_evidence_migration.sql` และรันใน Supabase SQL Editor ไฟล์นี้เพิ่มประวัติย่อและรูปโปรไฟล์, ตารางเบอร์ติดต่อส่วนตัวพร้อม RLS, snapshot เบอร์คู่สัญญาในรายการจอง และตาราง/Storage bucket `rental-evidence` แบบ private สำหรับรูปประกอบรายงานและขั้นตอนรับ–คืนสินค้า โดยไม่ลบข้อมูลเดิม และจำกัดสิทธิ์ UPDATE โปรไฟล์เป็นคอลัมน์ที่ผู้ใช้แก้ได้เท่านั้น

ผู้ใช้ตั้งค่าโปรไฟล์และเบอร์ส่วนตัวได้จาก **บัญชีของฉัน → โปรไฟล์** เบอร์โทรจะไม่แสดงในประกาศสาธารณะ และจะถูก snapshot เฉพาะรายการจองที่สร้างหลังติดตั้ง migration นี้ ภาพหลักฐานการรับ–คืนหรือรายงานเป็นตัวเลือก ไม่ได้แทนการยืนยันขั้นตอนจริง และเข้าถึงได้เฉพาะคู่สัญญา/ผู้รายงาน/แอดมินตามความเกี่ยวข้อง หาก SQL migration หรือการสร้าง bucket/policy มี error ให้หยุดและตรวจสาเหตุ ห้ามปิด RLS หรือทำให้ bucket เป็น public

### ตรวจ migration และลำดับติดตั้ง

อย่าสรุปจากไฟล์ใน repository ว่า migration ใดรันแล้วหรือยัง ให้ตรวจประวัติ migration ที่ใช้กับ Supabase project เป้าหมาย และตรวจ schema ปัจจุบันก่อนทุกครั้ง ห้ามรัน `schema.sql` ทับฐานข้อมูลที่มีข้อมูลแล้ว และอย่ารัน migration ที่ติดตั้งครบแล้วซ้ำโดยไม่ตรวจสอบผลกระทบ

สำหรับฐานข้อมูลใหม่ ลำดับพื้นฐานคือ:

1. `schema.sql`
2. `admin_upload_migration.sql`
3. `marketplace_features_migration.sql`
4. `chat_attachments_migration.sql` (ตัวเลือกสำหรับรูปภาพ/การ์ดรายการในแชต; ต้องรันหลัง marketplace)
5. `booking_lifecycle_migration.sql`
6. `rental_handover_reviews_reports_migration.sql`
7. `payment_deposit_migration.sql`
8. `profile_contact_evidence_migration.sql`
9. `service_fee_promptpay_payout_migration.sql`
10. `meeting_points_route_migration.sql`

ถ้าใช้ฟอร์มประกาศที่อนุญาตให้เว้นตำแหน่ง สภาพสินค้า หรือรายละเอียด ให้ตรวจและติดตั้ง `listing_optional_fields_migration.sql` หลัง `schema.sql` ก่อนเปิดรับประกาศดังกล่าวด้วย ลำดับนี้เป็น dependency ของโค้ด ไม่ใช่หลักฐานว่า migration ใดถูกติดตั้งบน project แล้ว

`promote_admin.sql` เป็นคำสั่งตั้งสิทธิ์ผู้ดูแลเฉพาะบัญชี ไม่ใช่ migration สำหรับรันตามลำดับ ให้ตรวจตัวตนบัญชีและรันแยกหลัง `admin_upload_migration.sql` เท่านั้น ส่วน `verify_rental_migrations.sql` และ `diagnose_migration.sql` เป็นไฟล์ตรวจสอบแบบอ่านอย่างเดียว ห้ามนำไปรวมใน migration ที่แก้ schema

ก่อนตัดสินใจรัน ให้ตรวจ `supabase/verify_rental_migrations.sql` และ Table Editor/SQL Editor ว่ามีตาราง คอลัมน์ RLS, policies, functions, triggers และ bucket ตามที่คาดหรือไม่ สคริปต์ตรวจสอบเป็น read-only และไม่ยืนยันประวัติการรัน migration; ตรวจ migration history ของ project แยกต่างหาก จากนั้นรันเฉพาะไฟล์ที่ยังขาดตามลำดับ โดยตรวจผลแต่ละไฟล์ก่อนดำเนินไฟล์ถัดไป หากพบ policy หรือ bucket เดิมที่มีสิทธิ์กว้าง/การตั้งค่าไม่ตรง ให้หยุดและตรวจสอบก่อน อย่าปิด RLS หรือเปลี่ยน bucket ให้ public

หาก migration แจ้งว่าค่า `notifications.kind`, `notifications.link_type`, หรือข้อมูลเดิมไม่ผ่าน constraint ให้รัน `supabase/diagnose_migration.sql` แยกใน SQL Editor เพื่อดู definition และจำนวนข้อมูลก่อน ห้ามลบหรือแก้ข้อมูลเพื่อให้ migration ผ่านโดยไม่ตรวจสอบสาเหตุ

## B. ตั้งค่า URL และ key ให้เว็บไซต์

1. ใน Supabase เปิด **Project Settings → API** (บางหน้าจออาจแสดง Project URL กับ API keys แยกตำแหน่ง)
2. คัดลอก **Project URL** และ **anon/public key** หรือ **publishable key** เท่านั้น
3. คัดลอก `.env.example` ในโฟลเดอร์โปรเจกต์แล้วตั้งชื่อสำเนาเป็น `.env.local`
4. แก้ `.env.local` เป็นลักษณะนี้ โดยแทนค่าตัวอย่างด้วยค่าจากโปรเจกต์ของคุณ:

   ```dotenv
   VITE_SUPABASE_URL=https://your-project-id.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
   ```

   ห้ามใส่ `service_role` หรือ secret key ในเว็บไซต์ฝั่งหน้าเว็บ และห้ามส่ง key ประเภทนั้นให้ใคร

## ตั้งค่าบัญชีแอดมิน

1. สร้างบัญชีอีเมล `phklxng@gmail.com` ใน Supabase Dashboard → **Authentication → Users → Add user** หรือสมัครจากหน้าเว็บก่อนก็ได้ ตั้งรหัสผ่านที่คาดเดายากและไม่ซ้ำกับบัญชีอื่น
2. เปิด SQL Editor แล้วรันไฟล์ `supabase/promote_admin.sql` เพื่อกำหนดชื่อแสดงและยกระดับบัญชีดังกล่าวเป็นแอดมิน
3. ผลตรวจสอบท้าย SQL ควรแสดง `is_admin = true` จากนั้นออกจากระบบและเข้าสู่ระบบใหม่ในเว็บ ปุ่มบัญชีจะเปลี่ยนเป็น **แอดมิน**
4. หน้าแอดมินมีแท็บภาพรวม ประกาศทั้งหมด การจองทั้งหมด และสมาชิกทั้งหมด โดยอีเมลสมาชิกจะดึงผ่าน RPC ที่ตรวจสิทธิ์แอดมิน ไม่ได้เปิดให้นักศึกษาทั่วไปอ่านจากตารางสาธารณะ

อย่าฝังรหัสผ่านไว้ใน JavaScript หรือ GitHub และอย่าใช้ `service_role`/Secret Key ใน `.env.local` ของ frontend เนื่องจากรหัสผ่านที่ส่งมาในแชตนี้ถูกเปิดเผยแล้ว แนะนำให้ตั้งรหัสผ่านใหม่เฉพาะบัญชีนี้ก่อนเปิดใช้งานจริง

เปิด URL ที่ Vite แสดง (ปกติ `http://localhost:5173`). หากเปลี่ยน `.env.local` ขณะเซิร์ฟเวอร์กำลังทำงาน ให้หยุดด้วย `Ctrl+C` แล้วรัน `npm run dev` ใหม่

ตรวจสอบว่ากล่องแจ้งสถานะบนเว็บบอกว่าเชื่อมต่อโหมดฐานข้อมูลแล้ว ไม่ใช่โหมดตัวอย่าง

## ฟีเจอร์แชต ข้อเสนอ และแผนที่

- แชตและแจ้งเตือนใช้ Supabase Realtime พร้อม polling สำรองเมื่อการเชื่อมต่อขาด โดย RLS จำกัดข้อมูลตามคู่สนทนา/ผู้รับ
- ความต้องการเดิมจาก `localStorage` จะถูกนำเข้าเมื่อผู้ใช้เข้าสู่ระบบครั้งแรกในเบราว์เซอร์นั้น ข้อมูลเดิมจะคงอยู่ในเครื่องและมี marker ป้องกันการนำเข้าซ้ำต่อบัญชี
- พิกัดเป็นข้อมูลไม่บังคับและไม่มีการเรียกตำแหน่งอุปกรณ์อัตโนมัติ ให้ระบุเฉพาะจุดรับสาธารณะโดยประมาณ ไม่ใช่ที่อยู่บ้าน
- แผนที่ใช้ OpenStreetMap tiles พร้อม attribution; การโหลด tiles ต้องเชื่อมต่ออินเทอร์เน็ต
- ผู้ดูแล/ผู้พัฒนาต้องตรวจสอบ RLS และทดสอบด้วยบัญชี Supabase สองบัญชีก่อนเปิดใช้งานจริง

## D. ตั้งค่าการยืนยันอีเมล

ถ้า Supabase ตั้งให้ต้องยืนยันอีเมล การสมัครจะส่งอีเมลให้กดลิงก์ก่อนจึงเข้าสู่ระบบได้ ใน Supabase ไปที่ **Authentication → URL Configuration** แล้วเพิ่ม `http://localhost:5173` ในรายการ Redirect URLs (ถ้ามีหน้าการยืนยันอีเมล ให้ทดสอบด้วยอีเมลที่คุณเข้าถึงได้)

สำหรับการทดสอบบนเครื่องเดียว สามารถใช้ผู้สมัครสองบัญชีที่แยกกัน: บัญชี A ลงประกาศ แล้วบัญชี B ส่งคำขอจอง จากนั้นกลับเข้าบัญชี A → **บัญชีของฉัน → คำขอที่ได้รับ** → อนุมัติหรือปฏิเสธ

## ข้อจำกัดและข้อควรระวัง

- URL/key ยังไม่ได้เชื่อมกับบัญชี Supabase ของผู้ใช้โดยอัตโนมัติ ต้องใส่ใน `.env.local` เอง
- `anon/public` key เป็นค่าที่ใช้งานใน frontend ได้เมื่อเปิด RLS ถูกต้อง แต่ห้ามใช้ `service_role`/secret key ในไฟล์ frontend
- รูปภาพอัปโหลดไปยัง public bucket `listing-images`; URL สาธารณะใช้สำหรับแสดงรูปเท่านั้น ส่วนการอัปโหลด/ลบไฟล์ถูกควบคุมด้วย Storage policies
- ค่าเช่าและเงินมัดจำคำนวณจาก snapshot ในรายการจอง ไม่มีค่าบริการแพลตฟอร์มหรือ Payment Gateway ระบบรับเฉพาะหลักฐานเพื่อให้แอดมินตรวจสอบ ไม่ได้ตัดเงิน/รับเงินจริงอัตโนมัติ และการบันทึกสถานะคืนเงินไม่ใช่การโอนเงินจริง
- คำขอที่รออนุมัติยังไม่ล็อกช่วงวัน เจ้าของต้องอนุมัติเพียงคำขอเดียวต่อรายการ/ช่วงวันที่; PostgreSQL จะป้องกันคำขอที่อนุมัติแล้วทับซ้อนกัน
- ก่อนเปิดให้ใช้งานสาธารณะ ควรทดสอบ auth, RLS, นโยบายการคืนของ, การรายงานปัญหา และแผนรับมือความเสียหายอย่างจริงจัง
